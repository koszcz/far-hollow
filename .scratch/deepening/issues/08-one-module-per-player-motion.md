# 08: Give each player motion its own module, so asset sessions stop colliding

**What to build:** Each animation asset that poses the player in code, such as hand crafting, sled dragging, or eating, lives in its own module. The module owns the motion's pose, its props, its constants, and its per-frame update. `src/render/player-mesh.ts` only runs the motions from a list. A new motion or a polished one touches its own file and one line of the list, not `player-mesh.ts`.

**Blocked by:** None

**Status:** ready-for-agent

**Assets:** None. This ticket changes no asset. Every animation must look the same before and after.

## Why

On 2026-11-21, six asset branches changed `src/render/player-mesh.ts` (1078 lines) in one afternoon. Landing two of them hit merge conflicts in it: the hand-craft animation and the sled rope.

The pose maths is already split out, into files such as `player-hand-craft-pose.ts` and `player-sled-drag-pose.ts`. The wiring is not. For each motion, `player-mesh.ts` still holds its constants, its props (the saw, the rod, the pot, the torch), its setter, its clause in the axe rule, its branch in the per-frame update, and its paragraph in the header comment. Polishing any one motion edits the same lines as every other.

The showcase half of the original ticket moved to ticket 09 during triage.

## Decisions already made

These were settled in triage on 2026-11-21. Read ADR 0012 first.

- One module per animation asset in the catalogue. The five eat and drink motions stay one module.
- Only motions posed in code move, plus the lit torch. Clip motions and the carried log stay in the player mesh.
- One generic `setMotion(id, moment)` call replaces the setters of the moved motions.
- The list order decides which body motion wins. Each motion declares whether the axe goes on the back.
- Three layers: `body`, `upperBody`, and `overlay`.

## What to do

The agent brief under Comments is the contract.

1. Add the rig, the motion interface, the motion list, and its `.gitattributes` line. Move gathering stone first, as it is the smallest.
2. Move debarking, sawing, building, crafting by hand, and fishing, one per commit.
3. Move eating and drinking, as the `upperBody` layer.
4. Move sled dragging, as the last body motion.
5. Move the lit torch, as the `overlay` layer.
6. Compare screenshots of every moved asset's showcase, then land.

## Acceptance criteria

- [ ] Adding a new motion posed in code adds one new module and one line to the motion list. It changes nothing in `player-mesh.ts`.
- [ ] `player-mesh.ts` holds no constants, props, or comments that belong to a moved motion.
- [ ] Every moved animation looks the same before and after. The screenshot comparison in the brief shows it.
- [ ] Existing tests pass.

## Agent Brief

**Category:** enhancement

**Summary:** Move each animation asset that poses the player in code out of the player mesh, into its own module, run from a list that git merges by union.

**Current behavior:**

- The player mesh (`createPlayerMesh`, which returns `PlayerMesh`) builds the Barbarian model and runs every player motion.
- Motions posed in code each have a pose module, such as `buildPoseAt`, `debarkPoseAt`, `sawPoseAt`, `handCraftPoseAt`, `fishPoseAt`, `gatherStonePoseAt`, `eatDrinkPoseAt`, and `sledDragPoseAt`. Most are wrapped in `createWorkMotion`, which tracks the start time and standing back up.
- Everything else about each motion still sits inside `createPlayerMesh`:
  - its constants, such as how big the stone or pot is in the hands
  - its props, built and disposed of there: drawknife, stone, saw, hand-craft bundle, fishing rod, line, float, caught fish, pot, and torch
  - a `place*` function for each prop, called from `pose()`
  - a setter on `PlayerMesh`, such as `setFishing`, `setHandCrafting`, `setDragging`, `setEatingOrDrinking`, or `setLitTorch`
  - a clause in the rule that puts the axe on the back, and in the check for what plays underneath eating
  - a paragraph in the header comment that names its asset and its approval
- The renderer calls each setter once per frame. `ropeHold()` and `torchFlame()` are read by the renderer for the sled rope and the torch light.

**Desired behavior:**

- Read ADR 0012. It is the design.
- Each of these animation assets becomes one motion module: `player-build-animation`, `debarking-animation`, `sawing-animation`, `hand-craft-animation`, `fishing-animation`, `gather-stone-animation`, `forage-eat-drink-animation`, `sled-drag-animation`, and the lit `torch` in the hand. A module may keep using its existing pose module, or absorb it.
- The player mesh lends each motion a **rig**: the player's group, the bones used for posing (the existing `BuildBones`, which includes both arms), a `material()` helper whose materials the mesh disposes of, and read-only state: whether a log is carried and the metres walked.
- Each module exports `create<Name>Motion(rig)`. A motion gives back:
  - `update(moment, now)`, built on `createWorkMotion`
  - `pose()`, absent for an overlay
  - `placeProps()`, run after every pose is applied
  - `dispose()`
  - its `layer`: `"body"`, `"upperBody"`, or `"overlay"`
  - `axeOnBack`: true for every moved motion except sled dragging and the torch
- A motion list module names every motion, in the order body motions win. It is marked `merge=union` in `.gitattributes`. A map type in it gives each motion id its moment type. For example, fishing takes the existing `Fishing` shape, and building takes a clock time.
- `PlayerMesh` gains `setMotion(id, moment | undefined)`, typed by that map. The setters of the moved motions go away. The renderer calls `setMotion` instead.
- `ropeHold()` moves into the sled-drag module, and `torchFlame()` moves into the torch module. `PlayerMesh` keeps both methods and passes them through, so the renderer does not change how it reads them.
- Rules that cross motions keep working the same way:
  - Starting any work motion ends standing back up. Stopping one stands the player up the way that motion does.
  - Standing back up eases out only over the idle clip.
  - Eating and drinking pose only the arms and head while the player walks, chops, splits, drags a sled, or does any body motion.
  - A hand steadying a carried log stays on the log. Only the left arm moves.
  - Sled dragging poses the body only when no other body motion plays.
- Each module's header names its asset and its approval state, moved from the player mesh header. The player mesh header keeps only the model, the beanie, the backpack, the clips, and the carried log.

**Key interfaces:**

- `PlayerMesh`: gains `setMotion`, loses the setters of the moved motions, keeps `ropeHold()`, `torchFlame()`, and every clip setter.
- `createWorkMotion` and `WorkMotion`: the base for each motion's start time and standing back up. Do not change how they behave.
- `BuildBones`, `BuildPose`, and `applyBuildPose`: how a motion poses the body.
- The showcases in `ANIMATIONS_SHOWCASES` and the renderer: the only callers of the setters that go away.

**Acceptance criteria:**

- [ ] A test or a typecheck shows that adding a motion needs only a new module and one line in the motion list. `player-mesh.ts` has no per-motion code for the moved motions.
- [ ] `.gitattributes` marks the motion list `merge=union`.
- [ ] `player-mesh.ts` holds no constants, props, `place*` functions, or header paragraphs that belong to a moved motion.
- [ ] The axe rule and the check for what plays under eating read `axeOnBack` and `layer` from the list. They name no single motion.
- [ ] Each commit moves one motion, and `bun test` passes after each one.
- [ ] For each moved asset, `bun scripts/shot.ts "/?asset=<id>" <out.png>` is run on `main` and on the branch, for every still shot. A script compares each pair. Do not open the images yourself (see `docs/agents/game-testing.md`).
- [ ] Any pair that differs beyond a small threshold is listed for the owner to check by eye, before `make land`.
- [ ] `bun run test:e2e` passes.
- [ ] `make check` passes.

**Out of scope:**

- Motions that only choose a clip: walking, chopping, splitting, sleeping, sitting, and reaching. The carried log also stays.
- Splitting the showcase files. That is ticket 09.
- Changing how any animation looks, or any asset entry in the catalogue.
- Changing the sled rope itself, beyond where it reads the rope hand from.
