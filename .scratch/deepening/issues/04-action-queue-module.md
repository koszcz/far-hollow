# 04: The action queue becomes its own module

**What to build:** The action queue lives in its own sim module. It asks each command's rule whether the action under way is done, instead of guessing from the player's task components. `src/sim/game.ts` only calls it each step.

**Blocked by:** 02

**Status:** resolved

**Assets:** None. This ticket changes no asset.

## Why

The action queue lives in closure variables inside `createGame` (`src/sim/game.ts:262-266`): `actionQueue`, `cancelCount`, and `castsWhenFishingBegan`. Its logic is spread over `sendOnItsOwn`, `queueAction`, `moveQueueOn`, and `endlessActionDone` (`game.ts:955-1024`).

It decides that an action is done when `playerIsBusy` (`src/sim/activity.ts`) finds no task component on the player. This guess has needed fixes:

- f41bf0e added one line to `TASK_PARTS`, so walking to lay a bedroll counted as work under way.
- d3ab2ac added fishing-only code to `game.ts`, so a queued fishing trip ends after one fish.
- `endlessActionDone` special-cases sitting and fishing by name.

It also spots "this command stopped what the player was doing" by comparing `cancelCount` before and after.

## What to do

The owner settled the design questions in triage on 2026-11-21. The agent brief under Comments is the contract.

1. Build the queue module with the interface the brief describes.
2. Move the queue state and its four functions into the new module.
3. Replace the sitting and fishing special cases with the rules' own answers.
4. Add a short unit test file for the module that does not need a whole game, if the interface allows it.

## Acceptance criteria

- [ ] `game.ts` holds no queue state. It calls the queue module to receive commands and to move on each step.
- [ ] Nothing in the queue module names sitting, fishing, or any other activity.
- [ ] A new action that never ends needs no edit to the queue module.
- [ ] Existing tests in `src/sim/action-queue.test.ts` pass unchanged.

## Agent Brief

**Category:** enhancement

**Summary:** The action queue moves out of `createGame` into its own sim module. The module names no activity. A command rule for an action with no end says when that action may stop for the next one.

**Current behavior:**

- The queue state lives in closure variables inside `createGame`: `actionQueue`, `cancelCount`, and `castsWhenFishingBegan`.
- Its logic is spread over `sendOnItsOwn`, `queueAction`, `cancelQueuedAction`, `moveQueueOn`, `startNextQueued`, and `endlessActionDone`.
- An action is done when `playerIsBusy` finds none of the parts in `TASK_PARTS` on the player.
- `endlessActionDone` names sitting and fishing. Sitting may stop at once when another action waits. Fishing may stop once a fish has bitten since the player began fishing. `applyCommand` resets the fishing mark on every command.
- `sendOnItsOwn` compares `cancelCount` before and after a command, to tell whether the command stopped what the player was doing.

**Desired behavior:**

- A new sim module owns the action queue: the action under way first, then those waiting. It is still not saved. Use the glossary term **Action queue** in names and comments.
- The queue behaves exactly as today for the player.
- An action is done when the player has nothing left to do. The queue asks this through one generic check, which stays `playerIsBusy` over `TASK_PARTS`. `TASK_PARTS` stays. Tickets 01 and 07 shrink it.
- A command rule may add one optional check, such as `canStopForNext()`. It applies only to an action with no end. The queue calls it only while the player is still busy and another action waits. If it returns true, the queue stops the action under way and starts the next one.
  - The sitting rule's check always returns true.
  - The fishing rule's check returns true once a fish has bitten on this fishing trip. The fishing module keeps the count of casts when the trip began. It does not save it, as the game does not today. Each fish command starts a new trip.
  - Today any command resets the trip, even pausing. After this ticket, only a fish command does. This is the one change in behaviour. Say so in the commit message.
- `cancelCount` goes away. Carrying out a command reports whether it stopped what the player was doing. The queue reads that report.
- The queue module takes what it needs from the game as plain functions or values. Examples are carrying out a command, the refusal check, the busy check, the rule's optional stop check, stopping the action under way, and showing a notice. This lets a test drive the queue without a whole game.
- `game.ts` holds no queue state. It passes received commands to the queue and moves the queue on after each logic step. A collapse still empties the queue.

**Key interfaces:**

- `CommandRule`: gains the optional stop check for actions with no end. Its comment says when the queue calls it.
- `GameView.actionQueue`: unchanged. The game reads it from the queue module.
- `playerIsBusy` and `TASK_PARTS`: unchanged in this ticket.
- The fishing module: gains the trip mark and the answer to "has a fish bitten on this trip".

**Acceptance criteria:**

- [ ] `game.ts` holds no queue state. It calls the queue module to receive commands and to move on each step.
- [ ] Nothing in the queue module names sitting, fishing, or any other activity.
- [ ] `castsWhenFishingBegan` and `cancelCount` are gone from `game.ts`.
- [ ] A new action that never ends needs a stop check on its own rule, and no edit to the queue module.
- [ ] A unit test file for the queue module drives it without creating a game. It covers at least: queueing up to the limit, a refused action skipped when its turn comes, and an action with no end that stops only when another action waits.
- [ ] Existing tests in `src/sim/action-queue.test.ts` pass unchanged.
- [ ] `make check` passes.

**Out of scope:**

- Saving the action queue.
- Changing the queue limit, or which commands can be queued.
- Removing `TASK_PARTS` or the task components. Tickets 01 and 07 do that.
- Moving command rules into their activity modules. Ticket 03 does that.
